## 1. Canonical Architectural Pattern Declaration

Hivelet is formally specified as a:

> **Layered Client-Server Architecture Structured as a Modular Monolith with a Pluggable Payment Gateway Adapter**

The declaration decomposes into three orthogonal commitments, each independently defensible:

1. **Layered Client-Server** — the browser never holds authority. The client is a rendering and input-collection surface; all authorization, all financial arithmetic, and all persistence decisions execute server-side (`backend/src/config/db.ts:9-14`).
2. **Modular Monolith** — every domain module executes inside one Node.js process against one PostgreSQL database, giving a single ACID boundary with no distributed coordination protocol.
3. **Pluggable Payment Gateway Adapter** — the Adyen GCash integration is confined to one replaceable module (`backend/src/services/adyenService.ts`) that resolves sandbox or live credentials at call time (`backend/src/services/adyenService.ts:42-50`), so the settlement provider can be substituted without touching the billing schema or the ledger.

The pattern is structured across **exactly five numbered tiers**, enumerated in Section 2.

> **Footnote on prior wording.** An earlier synonym, *"Isolated Payment Gateway Adapter,"* appears in the group's submitted presentation script at `docs/module_01_submission/FINAL_PRESENTATION_ARCHITECTURE_AND_DATABASE_DEFENSE.md:15` and in the master prompt block at `docs/module_01_submission/DEEP_TECHNICAL_ARCHITECTURE_AND_DATABASE_ANALYSIS.md:137`. *Isolated* and *Pluggable* denote the same adapter and the same code. A panelist quoting the earlier slide is quoting a valid synonym, not a contradiction. *Pluggable* is preferred going forward because isolation describes only the boundary, whereas pluggability additionally asserts substitutability of the provider behind it, which is the property the architecture actually buys.

Two descriptions of tier count in the submitted set are stale and are errata items: `docs/module_01_submission/02_SYSTEM_ARCHITECTURE.md:15` describes "four logical tiers," and the figure header at `docs/module_01_submission/DEEP_TECHNICAL_ARCHITECTURE_AND_DATABASE_ANALYSIS.md:19` reads "4-TIER MODULAR MONOLITH ARCHITECTURE" while the figure body immediately below it enumerates five. The canonical count is five.

## 3. The Four-Part Architectural Defense

### 3.1 Functionality — the architecture can express this property's actual rules

The property is **33 rentable units across 5 clusters**, seeded at `database/FULL_DATABASE_SCHEMA.sql:466-506` and locked as canon by BR-032 (`docs/02_BUSINESS_RULES.md:156`): BH main rooms 22 (1a-1h, 2a-2g, 3a-3g), Back Apartment 5 (B1F, B2F, B2B, B3F, B3B), Front Apartment 3 (F1, F2F, F2B), Penthouse 1 (PH), Linda 2 (LF, LB). The building form is **three residential floors plus a rooftop penthouse level**, and the per-floor distribution is owner-confirmed canon: **floor 1 — 11 units, floor 2 — 11 units, floor 3 — 10 units, floor 4 (rooftop penthouse) — 1 unit**, totalling 33. The Penthouse (`PH`) occupies that rooftop level alone and is the only penthouse on the property. The seed is the authority; `docs/01_SYSTEM_BIBLE.md:146` still reads "32 total rooms/units" and is an errata item.

*A note on vocabulary for the panel:* the family uses the word **Annex** to mean a **floor** (Annex A is the first floor), not a building. "Main Building," "Annex A," and "Annex B" are therefore not cluster names and do not appear in the data model. The stale usage at `docs/claude_pipeline/CLAUDE_PIPELINE.md:14` and `:140` is an errata item.

**Room-centric tenancy (ARCH-001).** The lease attaches to the unit, not to the person. BR-001 scopes the system to one property, BR-002 makes each unit uniquely identified by room number and floor context, BR-003 forbids silent deletion of history, and BR-032 fixes the unit list. This is why `room_assignments` is the join carrying `occupant_count` (`backend/src/routes/admin.ts:900-908`) rather than a column on the tenant profile: when a tenant leaves and another arrives, the unit's billing identity and history survive the turnover intact.

**Configurable water charge (ARCH-002 → BR-014, BR-034, BR-036, BR-040).** Water is `registered occupants x rate`, with the rate read from `system_settings.water_rate_per_occupant`, seeded at **200** (`database/FULL_DATABASE_SCHEMA.sql:454`, whose own `business_rule` column names BR-014). BR-036 (`docs/02_BUSINESS_RULES.md:174`) requires the system to warn rather than silently accept a mismatched manual entry. The architectural claim is that the rate is a **parameter**, not a constant — the parameter table exists (`database/FULL_DATABASE_SCHEMA.sql:441-450`) and is correctly seeded with six keys. The honest counterweight at the time of writing was that **`system_settings` was read by zero lines of backend code**, with the literal `200` compiled into three admin handlers and one tenant handler. **CLOSED 2026-09-13:** `services/settingsService.ts` is a typed cached reader over the table and `services/billingService.ts` applies the rate through it. No hardcoded rate remains anywhere in `backend/src`, and the public listing reads the figure over `GET /api/public/rates` rather than restating it in markup. The configurability is now runtime-real.

**Linda fixed-rate exception (BR-040).** Units LF and LB are excluded from the per-occupant model and carry fixed per-unit charges: `linda_lf_water_charge` PHP 400 and `linda_lb_water_charge` PHP 200, both corroborated against 31 months of the ledger. *(A third key, `linda_lb_electricity_charge` PHP 325, was retired by migration `017` per OD-18: it existed for units without their own meter, and the owner confirmed on 2026-09-13 that unmetered electricity will not be recorded in this system. The 31 historical rows totalling PHP 12,035.76 are preserved and read-only.)*, with the rule text at `docs/02_BUSINESS_RULES.md:190`. The exception is carried in the data model rather than in code branches: `rooms.is_linda_unit` is TRUE for exactly those two rows (`database/FULL_DATABASE_SCHEMA.sql:505-506`) and `monthly_income_records` carries `is_linda_billing`, `linda_electricity_charge`, and `linda_water_charge` (`:275-277`). A property that acquires a second fixed-rate unit changes one boolean and three numbers, not a billing algorithm. That is what a layered architecture is for.

**The BR-035 ledger-parity column.** BR-035 (`docs/02_BUSINESS_RULES.md:170`) defines the "50% Share" column as **exactly half of that row's Rent Amount, computed by the system and never entered manually**. It is a derived figure carried over from Column 6 of the landlady's existing source spreadsheet, retained so that the digital ledger reconciles line-for-line against her historical records. Water, the GBG garbage fee, and the deposit are excluded from it. Architecturally this is a *derivation*, and derivations belong in the service tier, recomputed from authoritative columns rather than stored as independently editable input — which is precisely why the present placement of the arithmetic inside route handlers (`backend/src/routes/admin.ts:911`, `:1102`) is a defect and not a design.

**Remittance and tenancy dates.** Remitted Amount = Rent Amount + Water Payment (BR-038, `docs/02_BUSINESS_RULES.md:182`); Deposit = the Rent Amount in effect at move-in, set once at onboarding (BR-039, `:186`); the monthly due date derives from the move-in date (BR-010, `:54`); a payment is overdue beginning the day after its due date (BR-011, `:58`); the grace period is read from `system_settings.grace_period_days` (BR-012, `:62`), originally seeded **7**, with the bill-creation path hardcoding **10** and contradicting both. **CLOSED 2026-09-13:** `billingService.ts` reads the setting through `settingsService`, and migration `016` set the value to **0** per OD-16, because this property grants no grace period. `grace_period_end_date` therefore equals `due_date`. The hardcoded window is gone.

**Rate Change History (ARCH-004 → BR-003).** Room rates are set **manually by the administrator**, and only when she decides to change them. The system proposes no adjustment, applies none on a schedule, and carries no rate-change rule of its own. What the architecture owes the property here is preservation, not automation: every change to a unit's rate is written to `room_price_history` (`database/FULL_DATABASE_SCHEMA.sql:136-145`), which records the previous price, the administrator-set new price, the date the new rate takes effect, and the administrator who made the change. This is BR-003 Historical Preservation (`docs/02_BUSINESS_RULES.md:15`) applied to pricing: `rooms.current_price` may move, but it never moves without leaving a dated, attributable record behind it, so a bill raised months ago stays reconcilable against the rate that was in force when it was issued.

**Settlement.** On-site in-person cash settlement remains the **primary** method, matching Mrs. Fe's daily office routine (FR-014, `docs/03_REQUIREMENTS.md:44-45`). Adyen GCash is the **optional digital alternative** (BR-016, `docs/02_BUSINESS_RULES.md:84`; FR-015, `docs/03_REQUIREMENTS.md:47-48`). The architecture does not require the landlady to change how she works in order for the system to be correct.

### 3.2 Security — one perimeter, one privileged client, one append-only record

**Express is the sole security perimeter.** `backend/src/server.ts:58` mounts a single `/api` router; there is no second ingress. Helmet installs a content-security policy at `:20-34`, CORS is a closed allow-list that rejects any unlisted origin at `:44`, the JSON body is capped at 1 MB at `:51`, and `trust proxy` is set at `:56` so that the client IP written into the audit trail is the caller's real address behind the university server's reverse proxy rather than the proxy's own.

**`service_role` containment.** Two Supabase clients exist, for opposite reasons (`backend/src/config/db.ts:9-14`). `db` holds the `service_role` key, bypasses RLS, and is reachable only after Express middleware has already established the caller's role. `publicProbe` holds the `anon` key and is deliberately powerless; its only job is to attempt a read of `profiles` (`backend/src/config/db.ts:72`) and assert that the read **fails**. If it succeeds, the boot sequence prints an explicit security alarm naming the unapplied migration (`backend/src/config/db.ts:80`, `:99-104`). The system therefore tests its own database lockdown on every start.

**RLS lockdown against the anon key.** Migration `002_rbac_rls_lockdown.sql` exists because, before it, every table in `public` was readable *and writable* by the Supabase `anon` key — a key published to the browser by design and additionally committed to `.env.example`. The migration's own header enumerates the exposure: tenant emails, phones and emergency contacts; the whole property's financial position; both ledgers; and world-**writable** `audit_logs`, which breaks auditability outright (`database/migrations/002_rbac_rls_lockdown.sql:11-22`). The remedy is deliberately belt-and-braces: RLS is enabled **and forced** on all 20 application tables so that even an owner-context connection is subject to policy (`database/FULL_DATABASE_SCHEMA.sql:558-559`); **no policy is defined for `anon` or `authenticated`**, so Postgres default-denies every row (`database/migrations/002_rbac_rls_lockdown.sql:33-36`); and privileges are revoked outright as a second layer that still denies access if RLS were ever toggled off on a table by mistake (`:117-123`, mirrored in the consolidated schema at `database/FULL_DATABASE_SCHEMA.sql:566-569`).

**Immutable audit trail (ARCH-007 → BR-018, BR-028).** BR-018 requires a financial correction to create an audit record containing the previous and updated values (`docs/02_BUSINESS_RULES.md:94`); BR-028 requires important administrative and financial actions to be traceable (`:138`). Immutability is enforced at the storage layer, not by convention: `UPDATE` and `DELETE` on `audit_logs` are revoked from `PUBLIC` and from every role **including `service_role`** (`database/FULL_DATABASE_SCHEMA.sql:572-573`; `database/migrations/002_rbac_rls_lockdown.sql:160-161`). The backend that writes the trail cannot rewrite it. `backend/src/services/auditService.ts:16-39` enumerates 23 audited action types spanning authentication, tenancy, billing, payment verification and correction, ticketing, and expense voiding. Authorization failures are audited automatically in the error path: every 401 and 403 is written to the trail before the response is serialized (`backend/src/middleware/errorHandler.ts:35-37`), so a probing attempt leaves evidence even though it accomplished nothing.

**bcrypt and JWT.** Passwords are stored only as bcrypt digests (`backend/src/services/authService.ts:11`; hashing at `:283` and `:346`, verification at `:83`). A login attempt against a non-existent account still performs a dummy `bcrypt.compare` against an invalid digest (`:71`), so response timing does not disclose whether an email is registered. Sessions are stateless HMAC-signed JSON Web Tokens, issued at `:152` and verified at `:157`.

**Guards and the permission matrix.** `requireAuth` re-reads the profile from the database rather than trusting token claims, so a deactivated tenant loses access on their very next request rather than at token expiry (`backend/src/middleware/auth.ts:73-89`). `requireRole` gates whole role-bound routers (`:98-112`); the admin router is gated in one line at `backend/src/routes/admin.ts:28`, the tenant router at `backend/src/routes/tenant.ts:33`. The preferred guard is `requirePermission` (`backend/src/middleware/auth.ts:123-138`), resolving against a single matrix in `backend/src/config/rbac.ts` — 35 named permissions (`:38-89`) across four roles. A guest holds exactly three (`:103-107`). A tenant holds nine own-scoped additions and is *deliberately* denied every `*:read:all`, both ledger permissions, payment recording and verification, ticket closure, and audit reading, with the governing rule cited inline beside each exclusion (`:109-134`). Holding an `:own` permission is only half the control — `scopeService.ts` narrows the query to the caller's rows from server-derived assignment data rather than from a client-supplied identifier (`backend/src/services/scopeService.ts:7-9`), and `requireSelfOrAdmin` blocks path-parameter tampering (`backend/src/middleware/auth.ts:146-161`). ARCH-006 maps to BR-006 and BR-048; the latter, admin-only authorship of the income and expense ledgers, is cited correctly in the RBAC file header at `backend/src/config/rbac.ts:5-6` and stated at `docs/02_BUSINESS_RULES.md:228`.

**Sovereign verification gate (BR-017).** A completed gateway transaction inserts a payment row with `verification_status = 'Pending Verification'` and **never auto-settles a bill**. Only the administrator's explicit verification action flips the bill and writes the income record (`backend/src/routes/admin.ts:836-1012`). BR-017 (`docs/02_BUSINESS_RULES.md:90`) and FR-016 (`docs/03_REQUIREMENTS.md:50-51`) place the landlady, not the payment processor, at the end of the money path. Architecturally this is what makes the gateway genuinely pluggable: no provider is trusted to mark a bill paid, so no provider is load-bearing.

**Two known security gaps, stated plainly.** Both are Phase 3 hardening items, not Phase 1 fixes, and both appear on the errata sheet.

1. **Two unauthenticated payment endpoints.** `GET /api/public/payments/mock-gateway` (`backend/src/routes/public.ts:201-202`) and `POST /api/public/payments/mock-gateway/complete` (`backend/src/routes/public.ts:852-853`) carry no `optionalAuth` and no `requirePermission`, unlike every other route on that router (compare `:47-48`, `:70-71`, `:90-91`, `:120-121`). They are reachable by session identifier alone. The blast radius is bounded — the sovereign verification gate means the worst outcome is an unverified `Pending Verification` row that the administrator rejects, not a settled bill — but bounded is not zero, and the correct posture is a signed, single-use, short-lived session token. The authenticated sibling route is correctly guarded (`backend/src/routes/tenant.ts:515-516`), which is what makes the omission on the public pair a defect rather than a deliberate exemption.

   > **Resolved in Phase 3 (2026-09-13).** Those two routes were the locally hosted checkout page, since renamed `/public/payments/local-cashier`. They now refuse to serve in any environment where Adyen credentials are configured, so they do not exist in a deployed system. The one remaining unauthenticated payment endpoint is the Adyen webhook, which cannot carry a JWT because a gateway holds none; it is protected by HTTP Basic Auth plus an HMAC-SHA256 signature over Adyen's payload, compared in constant time, and it is now the ONLY writer of an online payment.
2. **No explicit transaction boundary.** There is **no `BEGIN` / `COMMIT` anywhere in `backend/src`.** The submitted claim at `docs/module_01_submission/DEEP_TECHNICAL_ARCHITECTURE_AND_DATABASE_ANALYSIS.md:53` that four updates "execute inside an atomic database transaction (`BEGIN ... COMMIT`)" is an errata item: the *capability* is real and is the decisive reason to prefer a monolith, but the *code* does not yet use it. Today, verification performs a sequence of independent writes — bill update, income insert (`backend/src/routes/admin.ts:942-958`), notification insert (`:966-973`) — any one of which can fail after its predecessors have already committed. Atomicity is therefore a **Phase 3 design target**, discharged by `paymentService.ts` wrapping the sequence in a single database transaction.

### 3.3 Scalability & Maintainability — why a modular monolith is the correct ceiling for this property

The scaling question for Hivelet is not "how many requests per second" but "how many *independent failure modes* can a five-person undergraduate team reason about correctly." A modular monolith minimizes that number; microservices maximize it.

**No distributed two-phase commit.** Verifying one payment touches four tables: `bills`, `payments`, `monthly_income_records`, and `audit_logs`. In a monolith these are four statements inside one database, so a single `BEGIN ... COMMIT` makes them one indivisible unit. In a microservice decomposition — a billing service, a payments service, a ledger service, an audit service, each with its own store — the same operation requires a two-phase commit coordinator or a saga with compensating transactions, plus idempotency keys, plus a dead-letter path for compensations that themselves fail. The concrete failure this prevents is the one the panel should care about: a bill flipping to `Paid` while the corresponding income-ledger row is lost, leaving the landlady's ledger permanently out of balance against her cash position with no single place to look for the discrepancy.

**No network partition semantics between billing and ledger.** Billing and the income ledger are not two systems that must be kept in agreement; they are two projections of one financial event. Placing a network boundary between them would convert an invariant the database can enforce for free into an eventual-consistency problem the team would have to enforce in application code, correctly, forever. For 33 units this is negative engineering value.

**One ACID boundary, one deployable.** Twenty tables, one PostgreSQL instance, one Node.js process, one deployment artifact to the university server. Foreign keys, unique indexes, and check constraints perform enforcement work that would otherwise become hand-written cross-service validation. Deployment is one build; a rollback is one artifact. There is no service mesh, no inter-service gateway, no distributed tracing requirement, and no per-service on-call rotation — none of which a student team can staff, and none of which this property's load justifies.

**Right-sized to the operator, not to a hypothetical.** The tenant population is roughly 20 to 50 concurrent residents with one administrator. Read traffic is dominated by the public catalog, which is cached client-side and is the only thing the PWA caches. Write traffic is one administrator during office hours. A monolith is not a compromise at this scale; it is the correct answer, and the first component that would need to change under growth is the database, not the process topology.

**Deliberate omission of performance figures.** This document states **no** unverified performance number. The submitted claims of "under 256MB of RAM" (`docs/module_01_submission/02_SYSTEM_ARCHITECTURE.md:42`), "less than 50ms" and "100% data consistency" (`docs/module_01_submission/DEEP_TECHNICAL_ARCHITECTURE_AND_DATABASE_ANALYSIS.md:53`), and "sub-50ms query execution times" (`:116`) are unsubstantiated — no benchmark, load test, or profiling artifact exists in the repository to support them. They are errata items. Measured figures belong to the Phase 12 evaluation module, and the group will present measurements or nothing.

**The honest counterweight: modularity is currently a commitment, not an achievement.** The pattern's second word is *modular*, and today the codebase only partly earns it. **131 of 164 database calls (80%) sit in route handlers rather than in domain services**, and `backend/src/routes/admin.ts` alone is **2,263 lines**. The distribution is `admin.ts` 108, `tenant.ts` 17, `public.ts` 6 in the route tier, against 31 calls across the nine services that now exist. *(Recounted 2026-09-13. The route tier is unchanged at 131; the service tier grew from 27 to 31 as `settingsService`, `billingService`, `adyenWebhook` and `adyenWebhookHandler` were added, and `admin.ts` grew as request validation was put in.)* The consequence was visible elsewhere, though **not** in the example this paragraph originally gave. It claimed `fifty_percent_share` and `remitted_amount` persist `0.00` because the handler computes them and then omits them from the INSERT. That was wrong, and the correction is worth stating plainly: **CORRECTED 2026-09-13:** both columns are `GENERATED ALWAYS AS ... STORED` (`is_generated = 'ALWAYS'` in `information_schema.columns`), so PostgreSQL derives them and rejects any write naming them. Their absence from the INSERT is required. All 937 live rows hold correct values. The handler's in-line computation is redundant, not destructive.

The real cost of the thin service layer showed up in three places instead, each found by testing rather than reading: `replace_expense_allocations` raised 42804 on every call, so editing any expense allocation returned HTTP 500; the income-record write accepted `Infinity` for an amount, which PostgreSQL sorts above every numeric so the `CHECK (rent_amount >= 0)` constraint passed it; and the on-site payment path could report cash as posted to the ledger with nothing written. All three are the class of defect a service boundary prevents, because a service exposes one function that validates, computes and persists together, and a caller cannot perform half of it.

**How the commitment is discharged.** Phase 3 performs a **mechanical extraction**, not a rewrite. Each planned service in Section 5 is created by lifting the existing handler body into a typed function, replacing the handler with a call to it, and leaving the HTTP contract byte-for-byte unchanged so that the read-only frontend requires no modification. The sequence is: (1) `settingsService.ts` first, because it removes the hardcoded literals every other service would otherwise copy; (2) `billingService.ts` and `paymentService.ts` next, because they own the money path and are where the transaction boundary is introduced; (3) the remaining five in any order, having no cross-dependencies. Success is measured by one number falling: database calls remaining under `backend/src/routes/` should approach zero, with route files reduced to validation, guard composition, and service dispatch.

## 4. Alternatives Considered and Rejected

**Microservices.** Rejected because the dominant transaction in this system is a four-table financial write that must be all-or-nothing. Decomposing billing, payments, ledger, and audit into separately deployed services with separate stores converts a database transaction into a distributed one, requiring either a two-phase commit coordinator or a saga with compensating transactions and idempotency keys. For a property of 33 units with one administrator, this buys independent scalability that will never be exercised and pays for it with a permanent class of partial-failure bugs whose signature — a bill marked paid with no matching ledger row — is precisely the outcome the landlady would be adopting a system to prevent. The operational surface (container orchestration, service discovery, inter-service authentication, distributed tracing) also exceeds both the university deployment target and what a five-member undergraduate team can maintain past submission.

**Traditional server-rendered monolith (PHP/Blade, Django templates, or equivalent).** Rejected on two grounds specific to this property. First, connectivity: the boarding house serves students near Bicol University where mobile data is intermittent, and a template-rendered application requires a live round trip for every page transition, so an outage means no access to anything at all. The Vue 3 SPA with a scoped service worker degrades to a read-only view of the public catalog and health status instead of failing outright (`frontend/vite.config.ts:63-77`). Second, interface contract: the frontend is developed by a dedicated member against a JSON API, and a template architecture would couple view rendering to backend release cycles, removing the clean boundary that currently lets the backend be refactored — including the entire Phase 3 service extraction — without touching a single frontend file.

**Serverless functions (Lambda-style, or Supabase Edge Functions).** Rejected because the architecture's central security decision is incompatible with it as deployed here. Hivelet's perimeter is a single long-lived Express process holding the `service_role` key and enforcing a permission matrix in middleware before any query runs (`backend/src/config/db.ts:9-14`; `backend/src/config/rbac.ts:38-156`). Distributing that key and that matrix across dozens of independently deployed function handlers multiplies the number of places the perimeter can be misconfigured — and the two unguarded endpoints identified in Section 3.2 demonstrate how easily one route can ship without its guard even when every route lives in one reviewable file. Serverless additionally imposes per-invocation database connections against a connection-limited Postgres instance, cold-start latency on an administrator's interactive encoding workflow, and no natural home for a multi-statement transaction. The university server is a persistent host; a persistent process is the matching deployment model.
