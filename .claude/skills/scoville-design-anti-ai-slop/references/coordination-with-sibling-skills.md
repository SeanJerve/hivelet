# Coordination with sibling skills

Status: `draft`  
Intervention: `focus`  
Sources: `SRC-DESIGN-BOUNDARY-COORDINATION`, `SRC-PACKAGE-LOCAL-SYNTHESIS`

## Load when

An already active and applicable partner needs an actual exchange of design
intent, implementation constraints/evidence or wording inputs. Presence or a
name mention alone does not select this module. Do not discover, install,
require, simulate or load a sibling Skill because this module names it. Solo
phase work uses the Core record without this partner-only route.

## Shared handoff

Use only open relevant fields; otherwise use the Core minimal record:
`concern | canonical owner | decision/status | intended effect |
authority/source/version | preserved constraints | allowed variation |
exception/compensation/falsifier | validation target | evidence status | unknowns`.

Keep each owner's status vocabulary and field meaning. Approval, verification
and unresolved choice are separate dimensions. An observer adds attributed
effects without editing another owner's decision or approving its evidence.
Source-version changes invalidate affected decisions and require owner review;
an unresolved/invalidated field is not permission to choose freely. Carry the
smallest sufficient source or exact locator, not unsupported paraphrased approval.

## Design and the UI implementation partner

`scoville-ui-anti-ai-slop` is an optional Skill for framework-aligned UI
implementation and rendered/runtime proof. In this section, UI means that
already active and applicable partner, not a prerequisite for Design.

Design sends the subject thesis, hierarchy, typography/colour roles, visual
invariants, allowed variation, responsive transformation intent, protected
content and the evidence/unknowns that determine the design judgment.

UI returns actual framework/component constraints, implemented states and
semantics, accessibility/responsive behaviour, rendered/runtime evidence and
any conflict with the intent. UI owns framework-valid implementation; Design
does not bypass the incumbent system with a parallel token/component owner.
Design judges visual consequences using returned evidence, not imagined output.
UI may report a design conflict but does not silently replace accepted intent.
Resolve a conflict at its owner before dependent work.

## Wording owner

`scoville-scribe-anti-ai-slop` is an optional Skill for wording, meaning and
source fidelity. For that active-applicable partner or another actual wording
owner, send the exact
source facts/strings, intended message, audience/context, protected terminology,
available space and permitted edits. Receive proposed wording with source
fidelity, meaning/claim limits and unresolved questions intact. Design owns the
visual treatment, not new facts, naming authority or a covert content rewrite.
If wording is locked, solve the visual problem within that constraint; request
a content decision only when needed. Without an active partner, perform only
authorised wording work directly and preserve the same facts and constraints.

## Verify the exchange

Check that the next owner can identify the actual source/version, protected
dimensions, open decision and missing proof. Changed assumptions invalidate
only affected fields; preserve prior observations. A handoff document is not
evidence that implementation, accessibility, user testing or approval occurred.

## Ownership and claim ceiling

This module owns the exchange, not partner activation or another domain's
decisions. Format, code, image, data, rights, cultural, production and human
authorities retain their own acceptance. No partner is a prerequisite for
standalone authorised Design work.
